## ZIP reachability evidence

**Application ZIP 2.4.2:** ordinary core/formats/CLI dependencies on all shipped OSes. Patch application reads individual entries, rejects symlinks, canonicalizes names and streams bytes into controlled staging files; it does not invoke ZIP's bulk extractor or copy archive Unix permission bits. Font-patch composition similarly reads regular entries and rewrites ZIP bytes; NW.js handling reads/rebuilds an archive rather than bulk-extracting it to disk. These paths avoid the three advisory-triggering bulk-extraction operations; this is a source-level assessment, not a claim that ZIP 2 is patched or all archive attacks are impossible. (`crates/core/Cargo.toml:29`, `crates/formats/Cargo.toml:23`, `crates/cli/Cargo.toml:27`, `crates/core/src/patch/verify.rs:355`, `crates/core/src/patch/verify.rs:410`, `crates/core/src/patch/stream.rs:38`, `crates/core/src/font_patch.rs:251`, `crates/formats/src/tyrano_nw.rs:103`, `crates/formats/src/tyrano_nw.rs:368`)

**Updater ZIP 4.6.1:** separate Tauri updater dependency, Windows-only in its upstream manifest. The updater is registered by the desktop. Its normal download/install flow verifies the signature before installation; signed ZIP input can reach `ZipArchive::extract`, whereas the declared release manifest selects raw MSI artifacts for Windows. ZIP 4 supports symlink creation on Windows; its Unix permission-restoration block is compiled only on Unix. Thus the two Unix-permission findings are outside this Windows branch, while symlink-target handling remains conditionally reachable for a signed ZIP. (`Cargo.lock:5995`, `Cargo.lock:6024`, `apps/desktop/src-tauri/src/main.rs:55`, `scripts/generate-updater-manifest.py:17`; upstream sources read: `tauri-plugin-updater-2.10.1/Cargo.toml:177`, `tauri-plugin-updater-2.10.1/src/updater.rs:712`, `tauri-plugin-updater-2.10.1/src/updater.rs:728`, `tauri-plugin-updater-2.10.1/src/updater.rs:882`, `tauri-plugin-updater-2.10.1/src/updater.rs:904`; `zip-4.6.1/src/read.rs:886`, `zip-4.6.1/src/read.rs:907`.)

### Why the rejected ZIP upgrade stays rejected

Do **not** blindly repeat ZIP 2 → 9. The candidate reduced findings and passed its original focused/full gates, but independent replay found different interpretation of unflagged CP437/UTF-8 names and acceptance of malformed Unicode extra fields that ZIP 2 refused. Forced application could write a differently named file or accept an archive previously refused. The supported ZIP 9 interface did not expose enough information to preserve malformed-extra rejection. The parent withdrew all candidate product changes; the 6/12 baseline was restored without a fresh scan. Wait for a compatible upstream fix or an explicitly reviewed expansion of archive scope, with public filename/refusal/no-write regressions preserved. (`docs/B2-REMEDIATION-2026-10-26.md:94`, `docs/B2-REMEDIATION-2026-10-26.md:96`, `docs/B2-REMEDIATION-2026-10-26.md:100`, `docs/B2-REMEDIATION-2026-10-26.md:102`)
